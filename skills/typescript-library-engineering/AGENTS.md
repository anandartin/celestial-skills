# AGENTS.md — TypeScript npm library

A publishable TypeScript package with an explicit exports map, correct types for every consumer, a tracked public API and semver releases from changesets.

## Setup and commands
- dev: `pnpm dev`
- lint: `pnpm lint && pnpm typecheck && pnpm publint && pnpm attw --pack .`
- test: `pnpm test`
- build: `pnpm build`
- deploy: `pnpm changeset publish`
- install: `pnpm install --frozen-lockfile`

## Project structure
- `src/index.ts` — The public entry point; re-exports only what is part of the API
- `src/<module>/` — Implementation, one folder per concept, with tests beside the code
- `src/internal/` — Helpers that are never exported from the package
- `etc/<package>.api.md` — API report generated by API Extractor; changes show up in review
- `.changeset/` — One changeset per user-facing change, with its semver bump
- `examples/` — Small consumer projects (ESM and CJS) used as smoke tests
- `package.json` — exports map, files allow-list, sideEffects:false, engines and peerDependencies

## Code style
- Files: kebab-case.ts
- Tests: *.test.ts beside the file; *.test-d.ts for type-only tests
- Branches: type/short-description, e.g. fix/retry-backoff-jitter
- Components: Exported functions camelCase verbs; classes and types PascalCase; error classes end in Error

### Code
- Prefer small, pure functions and explicit types at module boundaries. _(Easier to test, review and change.)_
- Expose the API only through the exports map; every exported function has explicit parameter and return types and a doc comment with an example. _(Consumers cannot depend on internals, and the API report stays readable.)_
- Any removal, rename, narrowed input or widened output in the API report is a major version; additions are minor; fixes are patch. _(Consumers rely on semver ranges to upgrade without reading every release.)_

### Components
- Components read design tokens; no raw hex values, pixel sizes or font names in component code. _(One token change restyles the product.)_

### Data
- Analytics events are object_action in snake_case and come from the experience skill’s measures. _(Names stay consistent across teams and tools.)_
- Accept I/O dependencies (fetch, timers, storage) as options with sensible defaults instead of reaching for globals. _(Works across runtimes and is easy to test.)_

### Errors
- Every async action has loading, empty, error and success states, matching the experience skill. _(Unhandled states are where users get stuck.)_
- Throw subclasses of Error with a stable code property and the original error as cause; never throw strings. _(Callers can branch on codes that survive message rewording.)_

### Security
- Secrets never live in the repository; read them from the environment or a secret store. _(A leaked key outlives the commit that removed it.)_
- Validate every input on the server, even when the client already did. _(Clients can be bypassed.)_
- Web pages ship a Content-Security-Policy, HSTS, X-Frame-Options and nosniff. _(Cheap protection against the most common attacks.)_
- Publish only from CI with provenance and a granular, automation-only token; the files allow-list excludes tests, fixtures and source maps of private code. _(A hijacked laptop or a stray .env must not end up in a published tarball.)_

### Performance
- Keep sideEffects:false and no top-level work; prefer zero runtime dependencies, and frameworks only as peerDependencies. _(Bundlers can tree-shake unused exports and consumers avoid duplicate copies.)_

### Accessibility
- Use native elements first; add ARIA only when no native element fits. _(Native controls bring keyboard and screen-reader support for free.)_

## Testing and checks (must pass before a pull request)
| Gate | Tool | Threshold | When |
|---|---|---|---|
| Lint and types | The stack’s linter and type checker | 0 errors | Every pull request |
| Unit and component tests | The stack’s test runner | All pass; every design-skill component state covered | Every pull request |
| Dependency and secret scan | Dependency audit + secret scanner | No high or critical findings; no secrets | Every pull request and nightly |
| Package correctness | publint + @arethetypeswrong/cli on the packed tarball | 0 errors; types resolve for node16, bundler and ESM consumers | Every pull request |
| API report | API Extractor | Report committed and up to date; any change has a matching changeset with the right semver bump | Every pull request |
| Size budget | size-limit | Main entry ≤ 10KB minified and gzipped; no growth over 5% without approval | Every pull request |

## Pull requests
- Branching: Trunk-based: short-lived branches off main; maintenance branches only for supported previous majors.

**Review checklist**
- Correctness: does it do what the issue asks, including edge cases?
- Readability: could a new teammate change it safely?
- Architecture: is it in the right place, with the right boundaries?
- Security: inputs, secrets, permissions, dependencies
- Performance: budgets, queries, bundle size
- Tests fail when the code is broken (flip a condition and re-run)
- One approving review; two for any change to the API report
- Reviewer reads the changeset as release notes

**Definition of done**
- Acceptance criteria met and demoed on the preview link
- Tests added for new behaviour and every state
- Accessibility and performance gates green
- Analytics events named from the experience skill
- Docs or changelog updated when behaviour changes
- Changeset added for every user-facing change
- Doc comments and README examples updated and type-checked

**Release**
- Small pull requests (aim for under 400 changed lines)
- CI green before review
- Squash-merge to main; main is always deployable
- Every release has a written rollback path
- A release pull request collects changesets; merging it versions, tags and publishes from CI
- CHANGELOG.md generated from changesets in Keep a Changelog sections

**Incidents**
- Publish a fixed patch and deprecate the bad version with a message pointing to it
- Write a blameless note within 48 hours: what happened, impact, fix, prevention
